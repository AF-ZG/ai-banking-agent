# 系统架构说明

## 1. 总体架构图

```
┌─────────────────────────────────────────────────────────────────┐
│                        浏览器（前端展示层）                        │
│   index.html：聊天界面 / 三色确认卡 / 验证码弹窗 / 审计面板         │
│   JS 仅负责渲染，无任何本地业务逻辑，全部通过 fetch 调后端          │
```

**分层原则**：数据读写只发生在 mock_bank.py 一处；Agent 工具不直接碰文件；前端不做任何业务判断。任何一层可被独立替换（例如 mock_bank 换成真实核心系统，其余层零改动）。

## 2. ReAct 核心算法

ReAct = **Re**asoning（推理）+ **Act**ing（行动）。Agent 的每一轮对话是一个「思考 → 调用工具 → 观察结果 → 再思考」的循环，最多循环 `MAX_REACT_STEPS = 8` 步。

### 2.1 循环流程

```
用户输入
   │
   ▼
┌─────────────────┐
│ 拼装 messages    │◄──────────────────────────┐
│ system_prompt   │                            │
│ + 真实系统日期    │                            │
│ + 历史对话       │                            │
│ + 本轮输入       │                            │
└────────┬────────┘                            │
         ▼                                      │
┌─────────────────┐                            │
│ LLM 输出 JSON   │                            │
│ {thought,       │                            │
│  tool_name,     │                            │
│  tool_params,   │                            │
│  response}      │                            │
└────────┬────────┘                            │
         │                                      │
    tool_name 为 null？                         │
     │           │                              │
    是           否                              │
     │           ▼                              │
     │    ┌──────────────┐   工具结果            │
     │    │ 权限路由判定   │──────────────────────┘
     │    │ 绿:执行       │（结果追加进 messages，
     │    │ 黄:挂起+确认卡 │  进入下一轮思考）
     │    │ 红:挂起+验证码 │
     │    └──────────────┘
     ▼
返回 response 给用户
```

### 2.2 强制 JSON 输出协议

模型必须输出严格 JSON（`prompts.py` 中定义），由 `_extract_json()` 解析，容忍 markdown 代码块包裹：

```json
{
  "thought": "用户想给张三转账100元，参数齐全，调用转账工具",
  "tool_name": "transfer",
  "tool_params": {"payee": "张三", "amount": 100},
  "amount_clarified": false,
  "response": "已收到您的转账请求"
}
```

- `tool_name = null` 表示无需工具，直接回复用户（对话终止本轮循环）
- `tool_name != null` 时执行工具并把结果拼回上下文继续循环
- 单轮超过 8 步强制熔断终止，防止死循环

### 2.3 关键设计决策

- **系统提示词每轮注入真实日期**：`今天是 2026-09-28，本月为 2026-09-01 至 2026-09-28`，杜绝模型编造历史日期（时间幻觉防护）。
- **工具清单动态注入**：启动时通过 MCP `list_tools()` 拉取工具名和描述注入 system prompt，模型选择工具名有事实依据，不靠训练记忆。
- **确认/验证码均为独立轮次**：挂起的 `pending` 对象包含工具名、参数、权限级别、验证码，用户回复「确认」或验证码时直接执行挂起任务，不再问模型——权限决策权在代码层，不在模型。

## 3. DAG 任务规划

本项目未采用显式的 DAG 编排框架（如 LangGraph），而是以 **「ReAct 循环 + 权限路由状态机」** 实现等效的有向无环任务流。每个用户意图被分解为如下 DAG 结构：

```
                 ┌──────────┐
                 │ 用户意图  │
                 └────┬─────┘
                      ▼
              ┌──────────────┐
              │ 沙箱安全检查  │──── 拦截 ────→ [终止节点：红色警告]
              └──────┬───────┘
                     ▼
              ┌──────────────┐
              │ 意图解析      │──── 参数缺失 ──→ [终止节点：追问澄清]
              │ (LLM 推理)    │
              └──────┬───────┘
                     ▼
              ┌──────────────┐     ┌─ 绿色 → [直接执行] ──────────┐
              │ 权限分级判定   │─────┼─ 黄色 → [挂起] → 确认 ───────┤
              └──────┬───────┘     └─ 红色 → [挂起] → 确认 → 验证码 ┤
                     ▼                                             ▼
              ┌──────────────┐                            ┌──────────────┐
              │ 工具执行      │                            │ 执行 / 终止    │
              │ (MCP 调用)    │                            └──────────────┘
              └──────┬───────┘
                     ▼
              ┌──────────────┐
              │ 结果组织回复   │──→ [终止节点：返回用户]
              └──────────────┘
```

特点：

- **边代表状态流转，节点代表确定性动作**：除「意图解析」外全部节点由代码控制，模型只参与解析，不参与权限决策。
- **无环保证**：挂起状态下输入新需求不会开新分支，而是保持挂起并提醒（测试4验证确认对象不错位）；取消指令收敛到唯一终止节点。
- **熔断**：ReAct 循环步数上限、验证码 3 次尝试上限、银行服务不可用时工具返回 `{"success": false}` 优雅降级，均为 DAG 上的熔断边。

## 4. 多轮对话状态维护机制

### 4.1 状态存储位置

| 状态 | 存储 | 生命周期 |
|---|---|---|
| 对话历史 `history` | ReActAgent 实例（内存） | 会话存续期 |
| 挂起任务 `pending` | ReActAgent 实例（内存） | 直到确认/取消/验证码通过 |
| 模糊金额标记 `_amount_was_ambiguous` | ReActAgent 实例（内存） | 跨轮，澄清确认后清除 |
| 会话映射 | main.py `_sessions` 字典 | 服务重启或 `/api/reset` 时销毁 |
| 审计日志 | `logs/*.jsonl`（磁盘） | 永久追加 |

前端 `index.html` 只持有 `session_id`（`"web-" + 随机串`），不存任何业务状态；刷新页面后新会话自动建立，旧会话可经 `/api/reset` 清理。

### 4.2 三种多轮衔接场景

**① 省略上下文拼接**

```
轮次1: 用户「给张三转账」     → Agent 追问金额（pending 为空，history 留痕）
轮次2: 用户「100块」         → LLM 读 history 拼接为「给张三转账100元」→ 黄色确认卡
```

**② 模糊金额跨轮追踪**

```
轮次1: 用户「给张三转10qian」 → 代码正则检测到模糊金额，记入 _amount_was_ambiguous
                                 （关键：检测在「无需工具直接回复」分支之前执行，
                                  追问轮 tool_name=null 也会记录）
       Agent 追问「10元还是10000元？」
轮次2: 用户「是10元」          → 确认卡挂起时检查 _amount_was_ambiguous 非空
                                 → 确认卡附加大写金额加粗警告 + 审计落盘
       确认/取消后标记清空
```

**③ 挂起任务与取消语义**

- 有 `pending` 时：安全优先，任何含取消语义的输入（「算了」「取消」）一律终止挂起任务。
- 无 `pending` 时：只有「纯取消指令」才被拦截；「取消爱奇艺那个」这类带业务宾语的是新意图，放行给模型（`is_pure_cancel()` 区分二者）。
- 有 `pending` 时输入无关新需求：不执行、不吞掉，提醒当前挂起任务并要求先处理。

### 4.3 并发控制

`main.py` 为每个会话配一把 `asyncio.Lock`，同一会话的 `/api/chat` 与 `/api/action` 请求强制串行，防止确认/验证码状态被并发请求打乱。不同会话之间完全隔离，互不影响。
